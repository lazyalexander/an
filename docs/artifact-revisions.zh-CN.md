# 产物流设计（二）——产物的独立修订与跨文档块引用

会议纪要里产生一条「图书馆周一开馆」的决定时，它就应当有自己的身份。公告可以原样引用，行动清单可以据此写出「周一前更换门牌」。以后改为周二，只需修订一次决定。两份文档可以在不同时间采用新版，已经发出的公告仍能按原样打开。

## 产物从何时成立

对 An 而言，产生的时点是宿主第一次接受这份内容。人提交的决定、agent 提交的验收结论，以及 spool 输出中可独立流转的内容块，都在此时取得**产物 ID 和首个不可变版本**。即使一条决定首次出现于纪要内部，spool 也能在同一次提交里交回独立的决定和引用它的纪要。业务上怎样分块由内容生产者声明，文本解析和排版由相应的 spool 负责。

产物可以先在任务内保存，随后定向交接或发布。容器里的工作文件、自动保存和普通日志仍属于该次运行。需要把某段日志作为依据时，冻结所选片段并引用它。采纳决定、向主 agent 的 workspace 交付材料、向外部导出，都各自记录作用于哪个版本。

## 身份、版本和位置

| 要定位的东西 | 使用的标识 | 哪些变化会产生新版本 |
| --- | --- | --- |
| 同一项决定或验收结论 | 产物 ID 跨修订保持稳定，产物版本固定内容、依据和上一个版本 | 更正结论、增补依据都会产生新版本。即使正文相同，更换依据也是一次修订。 |
| 一块内容在文档里的使用位置 | 文档本身也是产物。其版本保存有序的块清单，每个位置有文档内唯一的块 ID | 移动保留块 ID，移除过的 ID 留给原块。新增、移除、重排或改为引用另一版内容，都产生新文档版本。 |
| 文件字节 | 产物版本指向不可变的文件快照。文本块可以用该快照内的相对路径和 UTF-8 字节区间定位 | 相同文件可共用快照。两个主体各自产生的同文结论，仍可有不同的产物 ID 和来源。 |

一条引用的两端都用 `产物 ID @ 版本 # 块 ID` 定位。下表中的名称和数字是便于阅读的示意。决定本身可以包含「结论」和「依据」两个块。公告中的「开馆时间」是它在公告里的使用位置。同一决定在一份文档出现两次，就有两个可分别追查的位置。

| 使用位置 | 关系 | 固定来源或核验对象 |
| --- | --- | --- |
| 开馆决定@1#结论 | 依据 | 会议原始记录@1#开放时间 |
| 纪要@1#议定事项 | 收录原文 | 开馆决定@1#结论 |
| 公告@1#开馆时间 | 收录原文 | 开馆决定@1#结论 |
| 行动清单@1#更换门牌 | 根据决定改写 | 开馆决定@1#结论 |
| 验收报告@1#时间核对 | 核验 | 公告@1#开馆时间 |

收录原文时，多处可以共用同一个内容块。改写产生带有来源引用的新内容，可在行动清单里单独修订。验收报告则固定它实际检查的版本。界面可以提示「已有新版」，保存、交接和交付一律使用调用者选定的具体版本。第一项设计规定了沿这些关系查询来源和影响时应给出的证据。[决定的来源与影响](artifact-flow.zh-CN.md)

## 一次修订怎样提交

1. **指明要改的对象。** 修订决定需要该产物的修订权限，提交时给出决定 ID、预期的上一版本、这次的内容及来源。只改公告措辞时，在有权修订的公告里提交新内容并指回原决定。若要从同一材料另立一项可独立演变的决定，分配新产物 ID，并保留它派生自哪个版本。
2. **核对块清单。** 每个受管文本块列明有署名的原始陈述或所用来源。An 检查块 ID 在版本内唯一，文本区间落在对应快照内，来源端点存在且属于本次获准使用的材料。首版对声明为原文的文本区间核对源块字节。改写的语义是否忠实，由验收者检查。拆分或合并内容时，给新块分配 ID 并列出各自的来源。
3. **一起落账。** An 在同一事务中核对预期版本，保存新版本、对应的文件快照、块清单、引用和提交回执。版本关联提交主体、任务以及产生它的执行尝试或人的响应事件。公告可以引用同批新建的决定，整批通过后才可见。收录原文产生循环、来源无法解析或超出授权时，整次提交失败，错误定位到提交者自己的块。成功提交的每条引用都可以从两端查询。
4. **处理并发与重试。** 两个提交基于同一版修订同一产物，先接受的一份推进版本，另一份收到版本冲突并可基于新版本重新提交。相同幂等键和相同内容返回原回执，复用该键更改内容会被拒绝。不同文档各自采用新版时，各按自己的上一版本提交。

例如，开馆决定修订到第 2 版后，单独提交「公告第 2 版采用开馆决定第 2 版」。此时，公告第 1 版、行动清单第 1 版和旧验收报告仍可按表中的端点打开。复核新版公告会产生一份明确指向公告第 2 版的验收记录。

核验一版公告、确认其中的决定和批准发布各自由谁负责，见[人、agent 与 An 怎样分工](decision-authority.zh-CN.md)。

## 可见范围与现有文件

发布公告时，要对随公告实际交给接收方的内容检查发布权限。如果某个 spool 只获准读取纪要中的一个文本块，交给它的输入只含该块的冻结内容。沿引用打开纪要原文、决定的私有依据或运行日志时，按所读材料重新检查权限。反查使用位置也只呈现调用方有权知道的文档和块。关闭任务后的回收从交付、保留的产物和活动图出发，沿版本历史和块引用保留仍需解析的版本及文件快照。

当前仓库已按文件集合的摘要保存 `revision`。工具传回非空文件时，已有的 `artifact` 记录关联该次传回的快照。图交付则记录绑定和冻结的文件版本。[文件版本存储](../src/store.rs) · [工具文件传回](../src/transfer.rs) · [图交付](../src/graph/scheduler.rs) · [任务关闭后的回收](../src/store/gc.rs)

首版设计复用这层存储，新增产物版本、修订关系和块清单。旧交付仍应能按原来的 ID 打开、导出和恢复。旧数据只有文件绑定时，查询标明「文件级来源」。只有在提交方提供可核验的分块后，新版本才报告块级精度。

## 首版无头验收

沿用会议纪要样例中的开馆日和免费登记条目，以下为待实现的验收用例。[会议纪要输入](../examples/minutes/minutes.json)

| 操作 | 预期结果 |
| --- | --- |
| 在发布前将决定收录到纪要，再由公告和行动清单分别采用 | 首次提交已有独立的决定 ID。两个下游块能查回同一来源，免费登记块保持自己的来源。 |
| 将开馆日改为周二，只更新公告，再重启宿主 | 新公告引用第 2 版决定。旧交付导出的字节与首次导出一致，行动清单仍引用第 1 版，旧报告仍指向它检查过的公告。 |
| 改动依据而保持正文相同，另在文档内移动、拆分一个块 | 依据变化产生新产物版本，可复用同一文件快照。移动保留位置 ID，拆分后的两个块均可回查原块，旧版本仍可还原。 |
| 并发修订同一版并重放成功的请求，再提交一条悬空引用 | 一个修订成功，一个收到冲突。重放返回同一回执。悬空引用所在的整批提交失败，正反向查询都看不到部分写入。 |
| 只把开馆日块交给 spool，再用只有公告读取权的身份查询 | spool 输入中找不到纪要的内部备注。读者能打开公告，尝试修改原决定被拒绝。私有依据及其他私有引用方保持不可见。 |
| 关闭原任务并回收，再用有权限的新任务打开旧交付 | 仍能取回旧决定和被引用的文件。只有文件绑定的历史交付仍可导出，并报告文件级精度。 |
